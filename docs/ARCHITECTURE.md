# Архитектура и модель безопасности

## Поток создания платежа

1. XenForo создаёт стандартный `PurchaseRequest`.
2. Провайдер проверяет, что включены реальные платежи, покупка не рекуррентная, а валюта — `RUB`.
3. Для ключа покупки берётся именованная блокировка MySQL. Она не позволяет двум параллельным запросам создать разные транзакции для одной покупки.
4. В локальный журнал `xf_evrik_platega_invoice` добавляется запись со статусом `CREATING`.
5. В Platega отправляются сумма, валюта, описание, адреса возврата, `payload` с ключом покупки и антифрод-метаданные пользователя.
6. Ответ API принимается только при корректном UUID транзакции, допустимом статусе и безопасном HTTPS-адресе перенаправления.
7. Локальная запись получает ID транзакции, адрес оплаты и статус `PENDING`.

POST-запрос создания не повторяется автоматически. Если соединение оборвалось после принятия запроса Platega, повтор мог бы создать вторую транзакцию. Вместо этого запись получает статус `UNCERTAIN`, после чего администратор сверяет её с кабинетом Platega и выполняет ручную проверку.

## Обработка уведомления

Уведомление принимается только через POST. До изменения покупки проверяются:

- заголовки `X-MerchantId` и `X-Secret`;
- существование локального счёта и стандартного `PurchaseRequest` XenForo;
- принадлежность счёта тому же платёжному профилю;
- ID транзакции и ключ покупки;
- сумма и валюта;
- текущий статус через отдельный GET-запрос к API Platega.

Данные callback не считаются самостоятельным доказательством оплаты. Решение принимается по ответу API, который дополнительно сверяется с локальным журналом.

## Состояния

| Локальный статус | Значение |
| --- | --- |
| `CREATING` | Запрос создания выполняется |
| `UNCERTAIN` | Результат создания неизвестен; автоматический повтор запрещён |
| `PENDING` | Транзакция создана, оплата ещё не подтверждена |
| `CONFIRMED` | Покупка выдана |
| `CANCELED` | Транзакция отменена до выдачи покупки |
| `CHARGEBACKED` | Возврат подтверждён, ранее выданная покупка отозвана |

Переход к `CONFIRMED` выдаёт покупку один раз. Переход `CONFIRMED → CHARGEBACKED` отзывает её один раз. `CHARGEBACKED` является терминальным состоянием: позднее подтверждение не восстанавливает покупку.

## Защита от параллельной обработки

Финальная обработка выполняется в транзакции базы данных после `SELECT ... FOR UPDATE`. Стандартное действие XenForo и обновление локального статуса входят в одну транзакцию. Если обработчик конкретной покупки завершится ошибкой, обе части откатываются, а Platega сможет повторить callback.

## Журналирование и секреты

В стандартный журнал XenForo записываются только источник обработки, ID транзакции и проверенный статус. Secret key, заголовки авторизации и полные тела ответов API не журналируются. Исключения HTTP-клиента заменяются нейтральными сообщениями без вложенного исходного исключения.

## Передаваемые персональные данные

Для проведения и антифрод-проверки платежа передаются ID пользователя, имя пользователя и корректный IP-адрес, если XenForo может его определить. Администратору следует отразить это в политике конфиденциальности форума с учётом применимого законодательства и условий Platega.

## Ручное восстановление

Раздел **Платежи Platega** позволяет:

- найти запись по ключу покупки или ID транзакции;
- отфильтровать операции по статусу и профилю;
- увидеть зависшие `CREATING`/`UNCERTAIN`/`PENDING` записи;
- запросить актуальный статус и безопасно применить подтверждение или возврат;
- привязать ID транзакции из кабинета Platega к записи `UNCERTAIN`, если API подтвердит совпадение `payload`, суммы и валюты.

Ручная проверка использует ту же блокировку строки и те же проверки, что и callback, поэтому повторный запуск не выдаёт покупку второй раз.

## Границы ответственности

Дополнение не создаёт возвраты, не выполняет выплаты и не поддерживает автосписания. Оно принимает результат Platega и вызывает стандартный обработчик покупки XenForo. Возможность корректно отозвать покупку после возврата зависит от реализации конкретного purchasable-handler.
